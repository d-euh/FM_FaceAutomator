# FM Face Automator 개발 인수인계

작성: 2026-11-26, 한국 시간. 코드 확인 기준: `bb287fe`.
이 문서는 이전 대화에 접근할 수 없는 다른 계정의 개발자를 위한 현재 상태 요약이다.
실제 코드·최신 커밋이 이 문서와 다르면 차이를 확인한 뒤 최신 상태를 우선한다.

## 1. 새 계정에서 먼저 할 일

1. GitHub `d-euh/FM_FaceAutomator`의 `main`을 가져온다.
   저장소: https://github.com/d-euh/FM_FaceAutomator
2. 해당 환경의 `AGENTS.md`를 먼저 확인한다. 이번 확인 시 저장소 안에는 없었다.
3. 이 문서 → `README.md` → `README.ko.md` → `docs/squad-investigation.md` 순서로 읽는다.
4. `git status`, 최근 커밋, 아래 지원 범위와 미해결 항목을 확인한다.
5. 필요한 개발 환경과 GitHub 권한을 새 계정에 연결하고 테스트를 실행한다.

이전 계정의 대화·첨부파일·Cloud 설정·`/tmp`·가상환경·SDK에 접근할 수 있다고 가정하지 않는다.
소스와 배포 DLL은 커밋되어 있지만 실제 게임 파일·세이브·개인 진단 전체는 코드 저장소에 없다.
다른 계정이 같은 실행 중 Cloud 컴퓨터를 그대로 공유할 수 있는지는 확인되지 않았다.
새 계정의 별도 환경에서 GitHub 코드와 이 문서를 기준으로 재개하는 방식이다.

## 2. 사용자 요청과 작업 원칙

- 한국어로 간결하게 설명한다. 요청한 일은 가능한 부분부터 끝까지 수행한다.
- 코드를 바꾸는 작업은 검증 후 GitHub에 푸시하고 결과·검증 범위·남은 한계를 보고한다.
  기존 작업은 로컬 `work` 브랜치에서 `git push origin HEAD:refs/heads/main`으로 반영했다.
  새 환경의 브랜치·권한은 다시 확인한다. 파괴적 덮어쓰기나 강제 푸시는 하지 않는다.
- 사용자가 적용한 ponytail(full): 요구를 완전히 해결하는 최소 변경, 기존 공통 코드 재사용,
  불필요한 기능·의존성·추상화 금지, 중요한 분기에는 작은 회귀 테스트를 남긴다.
  이 계정의 스킬 설치 여부와 무관하게 이 작업 원칙은 유지한다.
- 실게임 관찰 / 실제 세이브의 정적 검사 / 모의 테스트 / 아직 확인하지 않은 가정을 구분한다.
- 선수단은 검증된 게임 관계와 세이브 참조로 분류한다. 나이·계약·슬롯·이름·숫자 하나로 추측하지 않는다.
- 영입은 새 구단/등록 팀, 방출은 이전 구단/등록 팀을 기준으로 동일한 선택 범위에서 판단한다.
- 제한한 범위의 팀 구분이 불명확하면 AI를 호출하지 않는다.
- 기존 설정·작업 기록·원본 사진·유니폼·페이스팩·관련 없는 XML 매핑을 보존한다.
- 이미 생성한 원본/완성 PNG는 재사용한다. 검증 과정에서 유료 AI를 임의 호출하지 않는다.
- 새 게임 빌드 지원은 파일·서명·동작 근거 없이 숫자만 바꿔 허용하지 않는다.
  네이티브 콜백 수명, 진행 가드, 오류 정리 절차도 보존한다.
- 사용자가 단지 문구를 물어보거나 복사할 글을 요청하면 제품 파일까지 임의 변경하지 않는다.

Plus 계정의 합성 성공은 사용자가 확인했다. Go 및 다른 요금제의 실제 이미지 합성은 미확인이다.
CLI 로그인 성공과 이미지 생성 도구 이용 가능 여부를 같은 것으로 취급하지 않는다.

`fmsave`에 이미 등록된 구형 FM27 빌드의 기존 기본 읽기 동작은 남아 있지만,
새 세이브 팀 분류의 지원 목록은 위 두 빌드뿐이다. 알 수 없는 미래 빌드는 계속 거부한다.

## 5. 완료한 주요 작업

### 세이브 기반 팀 분류 및 이적 처리

- 초기에는 게임 실행 중 팀 조회 DLL을 사용했다. 이후 실제 게임 참조와 세이브를 대조한
  검증을 거쳐 `74bca4d`에서 세이브 기반 판정을 앱에 연결했다.
- `0f78ba7`에서 앱의 팀 조회 DLL 호출·설치·연결 확인·관련 배포 리소스를 제거했다.
  `team_reader.py`, `team_bindings.py`, `plugin-src/FMTeamBindings/`와 조사 도구는
  과거 검증 재현용으로 남아 있다. 현재 앱의 분류에 다시 연결하거나 설치 대상으로 되돌리지 않는다.
- 저장된 팀 테이블을 한 번 읽어 `save_squads` SQLite 테이블에 기록한다.
  선수마다 전체 테이블 JSON을 복사하거나 작업마다 게임을 재조회하지 않는다.
- 분류 규칙과 상태 조합은 실게임 대조에서 관찰한 범위에 제한된다.
  `VERIFIED_STATES`, 최대 관찰된 하위 팀 구조, 소유 구단 검증을 임의로 완화하지 않는다.
- B팀은 부모 구단 관점에서 무조건 리저브가 아니다. 저장 구단과 판정 구단이 다르면 unknown이다.
- 자유계약 이전의 마지막 유효 등록 팀과 판정 근거를 보존한다.
  패치 전 빌드에서 얻은 이전 팀 근거도 패치 후 방출 판정에 사용할 수 있도록 했다.
- 선수단을 제한했는데 방출 전 등록 기록 자체가 없는 선수는 감지/대기열에서 제외한다.
  등록 ID는 있지만 구분이 unknown인 경우 등은 별도의 보류 경로가 있다.
- 과거 세이브를 골라 방출 기록을 복구하는 UI 기능은 사용자 요청으로 되돌렸다. 재도입하지 않는다.
- 저장 직전에 실시간 게임 팀 구분을 재조회하지 않는다.
  스냅샷·소속·범위가 같은 저장 근거는 재사용하고, 세이브 변경은 엄격히 확인한다.
- `21a08cc`: 27.1.1 실제 파일을 비교한 뒤 읽기·팀 분류 허용 목록에 추가했다.
  근거의 build는 항상 실제 파일 빌드이며 파서 버전은 `save-squads-v1`이다.

  실제 Google API·개인 계정·Windows 인증 창·합성 품질 검증은 하지 않았다. DLL 변경도 없다.

### UI·대기열·사용성

- 대기열 Ctrl/Shift 다중 선택, 선택 재시도·삭제·순서 변경과 우클릭 메뉴 구현.
  더블클릭은 작업 상태에 따라 개별 지시 편집/결과 보기로 연결된다.
- 담당 구단 우선순위는 같은 갱신에서 새로 들어온 작업끼리만 적용한다.
  이미 대기열에 있는 작업과 사용자가 정한 순서를 추월하지 않는다.
- 새 작업이 들어오면 완료 항목은 화면에서 숨기되 이미지·작업·호출 기록은 남긴다.
- `fa7daad`: 직접 생성 중에도 다른 선수의 직접 요청을 별도 연결로 등록할 수 있다.
  요청 등록 중/로그인 중의 잠금과 같은 선수의 실행·저장·편집 중 보호는 유지한다.
  자동 생성이 꺼진 일회성 처리 중 추가한 요청은 대기열에 남고, 자동 생성을 시작하면 계속 처리한다.
- 최초 실행의 경로 자동 찾기가 끝난 뒤 폴더·연결 설정 창을 연다. 이후에는 홈으로 시작한다.
- 공통 지시를 설정 창에 고정 표시하고 자동 새로고침 체크박스는 홈 버튼 옆으로 옮겼다.
- 사용자 제공 보라색/흰색 FFA 아이콘을 적용했다. Windows DPI·EXE 내장 아이콘 검사도 추가했다.
- 둥근 버튼과 탭 섹션을 조정했고, 패널 이미지의 1픽셀 중앙 타일링 때문에 느려지던 경로를 고쳤다.
  과거 둥근 패널 변경은 되돌림을 여러 번 거쳤으므로 현재 코드/커밋이 기준이다.
- 참조사진 미리보기 영역을 클릭해도 사진 선택 창이 열린다.
  사진을 생략하고 생성 요청하는 것만으로 선택 창이 자동으로 열리지는 않음을 Tk에서 확인했다.

### 성능·데이터 보존

- 미리보기용 참조 사진을 최대 512×512로 제한하고 원본 요청 경로/데이터를 보존한다.
- DB 대시보드 조회를 Tk 메인 스레드 밖으로 이동하고 오래된 응답이 UI를 덮지 못하게 했다.
- 선수 검색은 종류별 최신 요청을 취소/교체하고 표시·작업 수를 제한한다.
- 캐시 새로고침 시 이전 카탈로그와 traceback이 오래 남지 않도록 정리했다.
- 최근 결과 조회·사진 미리보기·로그의 보관량을 제한했다.
- 초기 경로 탐색은 설정된 항목의 전체 재검색을 생략하고 XML 앞부분 최대 256KiB만 분류에 사용한다.
- PNG/XML 적용 및 복원 실패 시 두 파일을 이전 상태로 되돌리도록 트랜잭션을 보강했다.
- 상세 수치와 재현은 `docs/code-review-2026-11-23.md`의 ‘후속 수정 및 재검증’을 읽는다.
  Linux 측정값을 Windows 전체 RAM/성능 보장으로 설명하지 않는다.

### 설치·배포

- 두 EXE를 만드는 PyInstaller onedir + Inno Setup 설치본을 구현했다.
- 생성 ZIP은 Setup EXE와 README.txt 두 파일만 포함한다.

## 7. 바로 이어서 조사할 미해결 문제

### A. 5대 리그 필터가 시즌 중에도 ‘일정 확인 못함’으로 표시됨

### B. ‘검색 파일이 너무 많습니다. 검색 범위를 좁혀주세요.’

정확한 발생 지점은 `assets.py`의 AssetCatalog 전체 탐색이며 파일 1,000,000개 초과 시 발생한다.
사진뿐 아니라 전체 파일을 세고, 하위 폴더도 포함한다. 폴더 한도는 20,000개다.
이는 초기 자동 찾기 `discovery.py`의 폴더 10,000개 제한과 다르다.

- 사용자에게 현재 기존 페이스팩/키트 경로를 요청했지만 **아직 답을 받지 않았다.**
- graphics 전체를 지정한 것인지, 정상적인 대형 팩 자체가 한도를 넘는지 먼저 구분해야 한다.
- 다중 팩·하위 폴더·같은 선수 우선순위·누락/중복 XML 검증을 보존한다.
- 단순 제한 해제/증가는 RAM·검색 시간 문제를 키울 수 있다. 아직 최적화 패치를 하지 않았다.

### C. 그 외 확인·미구현 항목

- 이름 스타일 예시 `BRUNO FERNANDES`는 `app.py:draw_name_preview`의 하드코딩이다.
  사용자 요청으로 정한 문구가 아니며 사용자가 이유에 이의를 제기했다.
  PLAYER NAME 같은 중립 문구가 더 적절하다고 답했지만 **실제로 변경하지 않았다.**
- ‘도움말·문제 해결’로 버튼 이름을 바꾸는 방안을 제안했지만 아직 구현하지 않았다.
- 읽기 전용 오류는 정확한 문구/진단 미수신. SQLite readonly, WinError 5,
  AI가 반환한 readonly sandbox 설명, 진단 보고서 형식 오류를 구분해야 한다.
- Claude CLI와 FM24 동시 지원은 조사·구현 전이다. Gemini API CLI는 위의 제한 범위로 구현했다.

  요금제 상세 페이지가 당시 네트워크 제한으로 열리지 않았다. Plus만 가능하다고 단정하지 않는다.
- 웹 검색의 생일 불일치는 앱의 무조건 보류 조건이 아니다. 웹 신원 확인을 AI가 못 하면 보류할 수 있다.
- 이미지 프롬프트의 구도 보존 변경 후 실제 결과가 항상 원본과 일치하는지 검증하지 않았다.

## 8. 저장·회복·자주 오해한 동작

- 게임이 꺼져도 지원 세이브 읽기·이적 비교·팀 분류·직접 생성·PNG/XML 저장이 가능하다.
  게임 내 새로고침만 게임 연결이 필요하다. 최근 회귀 테스트는 AI 결과를 모의 처리했다.
- 앱이 꺼져 있던 동안의 이적도 기존 기준 기록이 있으면 최신 저장본과 비교해 감지한다.
  첫 기준이 없으면 소급할 수 없고, 중간에 여러 번 이동했다 되돌아온 전체 과정은 알 수 없다.
- 사진은 선수 ID 매핑으로 게임 자료 폴더에 적용된다. 세이브별로 자동 분리/복원되지 않는다.
  새 커리어에서도 동일 팩을 쓰면 이전 유니폼 사진이 남는다. 게임에 적용할 팩은 사용자가 구분한다.
- 원본 사진 검색은 하위 폴더를 포함하고 상대 폴더 이름상 뒤의 팩을 우선한다(A보다 Z).
  이것은 앱의 참조 선택 규칙이며 인게임 로드 순서의 보편적 보장과는 다르다.
- UI의 ‘플러그인 연결 대기’는 생성 실패와 별개다. 최신 DLL이 healthy인데 앱에 대기가 남으면
  실제 EXE가 최신 client profile을 아는지와 자동/수동 polling 여부를 먼저 본다.
- 예전 client 코드와 최신 client에 동일 사용자 session을 넣은 재현에서 전자는 연결 대기,
  후자는 연결됨이었다. 사용자 EXE가 구형이었다고 단정한 것은 아니며 당시 보고서에는 실행 경로/기능 버전이 없다.
- 앱 배지 v1.0은 여러 패치에서 유지됐다. v1.0 표시만으로 최신 코드라고 판단할 수 없다.
- 최초 설정 재현은 앱 종료 후 config.json을 백업 이름으로 바꾸면 된다.
  전체 기준/작업 초기화는 해당 state/workspaces까지 백업해야 한다. 원본 사진/페이스팩을 지우지 않는다.
- config.json의 state_dir/workspaces가 사용자 지정 절대 경로일 수 있다.
  설정 파일 위치가 달라지면 별도 데이터로 시작할 수 있다. 기본 위치만 보고 기록을 없애지 않는다.
- paid_results, jobs 하위 portrait.png/result.png/request.json 등은 유료 결과 복구에 쓰인다.
  ‘캐시 정리’라는 이유로 일괄 삭제하거나 실패 결과를 자동 유료 재생성하지 않는다.

## 9. 빌드·설치·로컬 갱신

### Windows 소스 실행

```bat
setup_windows.bat
start_windows.bat
```

개발용 Python 3.12 이상과 Tk가 필요하다. 받는 일반 사용자는 Python이 필요 없다.
요구 패키지: `fmsave==0.12.6`, `Pillow==12.3.0`.

### 설치 ZIP 빌드

```bat
git pull origin main
build_windows.bat
```

- Windows x64 / 64비트 Python에서 빌드한다. PyInstaller 6.22.3을 사용한다.
- Inno Setup 6.3 이상이 필요하다. 7도 사용했고 자동 탐색이 안 되면 예를 들어:

```bat
build_windows.bat --iscc "C:\Program Files (x86)\Inno Setup 7\ISCC.exe"
```

- 출력: `dist\FMFaceAutomator-v1.0-windows-x64.zip`.
- 내부: `FMFaceAutomator-Setup-v1.0.exe`, `README.txt`.
- 별도 포터블: `build_windows.bat --portable` → `dist\FMFaceAutomator-Portable-v1.0-windows-x64.zip`.
- 설치 EXE는 프로그램을 인터넷에서 다운로드하지 않는다. 번들 파일을 설치 폴더에 푼다.
  Codex, 사진·키트, BepInEx는 별도 준비한다.
- `dist\FMFaceAutomator`에 있던 옛 EXE를 빌드가 갱신해 주지 않는다.
  **새 ZIP을 풀어 Setup을 실행하고 기존 실제 설치 폴더에 설치해야 한다.**
  이 차이 때문에 과거 v0.17.0 또는 오래된 v1.0이 계속 실행되는 혼선이 여러 번 있었다.
- 기본 설치 위치는 `%LOCALAPPDATA%\Programs\FMFaceAutomator`이다.
  기존 D드라이브 설치 등은 유지하므로 경로를 일괄 변경하지 않는다.
- 배포용 일반 README 원본은 `docs/DISTRIBUTION_README.txt`이며 빌드 시 UTF-8 BOM/CRLF README.txt로 들어간다.
  사용자가 최종 ZIP의 README를 직접 수정한 버전도 있다. 그 문안은 저장소 원본과 다르며
  다음 빌드로 자동 승계되지 않는다. 최종 배포 문구를 사용자에게 확인한 뒤 동기화한다.
- 업로드 ZIP 검사는 CRC/두 파일 구성/문구까지 했다. Inno Setup 7.1.1 EXE 내부는
  사용 가능한 innoextract 1.9로 풀리지 않아 최신 코드 포함이나 설치 후 총용량을 확정하지 못했다.
- 앞서 받은 ZIP은 약 17.7MB, Setup은 약 18.6MB였다. 설치 후/사진 포함 총용량 수치로 쓰지 않는다.

### 새로고침 DLL 설치

FM27 종료 → 최신 앱과 DLL 자료 준비 → 설치본의 `install_live_refresh.bat` 또는
Windows 시작 메뉴의 ‘게임 그래픽 새로고침 DLL 설치’ → 게임 재실행·세이브 로드 → 홈 버튼 테스트.
BepInEx가 없으면 호환 배포본을 먼저 fm.exe 옆에 설치하고 한 번 실행해 초기화한 뒤 종료한다.
기존 호환 BepInEx를 앱이 재설치/교체하지 않는다.
소스의 같은 이름 BAT는 `.venv`의 Python 도구를 실행하고, 배포본 BAT는 FMFaceTools.exe를 실행한다.

### 네이티브 코드/조사 도구

.NET 8 SDK로 테스트를 실행한다. DLL 본체는 net6.0이며 BepInEx/Core/IL2CPP/Harmony 참조가 필요하다.
완성된 0.2.4 DLL과 SHA256SUMS는 커밋되어 있어 일반 Windows 앱 빌드에는 네이티브 재빌드가 필요 없다.
C# 수정 시 `plugin-src/FMFaceRefresh/README.md`와 프로젝트 파일을 확인하고 SDK를 별도로 확보한다.
DLL을 다시 만들면 `plugins/FMFaceRefresh/FMFaceRefresh.dll`과 체크섬도 함께 갱신한다.

새 게임의 정적 자료가 필요하면 `export_refresh_compatibility.bat`를 사용한다.
출력 `diagnostics/refresh-compatibility.json`은 게임 파일 해시·PE API 서명이며 DLL/API를 실행하지 않는다.
`tools/FMRefreshMetadata`는 조사 전용이고 보통 앱 설치 ZIP에 포함하지 않는다.
`verify_save_team_roles.bat` 등 옛 실시간 팀 대조 도구는 26620374 조사용이다.
새 게임에서 실행하도록 제한을 무작정 바꾸지 않는다.

## 10. 새 환경 테스트 방법과 최신 검증

Linux 예시(Python/Tk가 설치된 환경):

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -v
```

GUI가 없으면 일부 Tk 테스트는 skip된다. Xvfb가 있다면 다음처럼 GUI 테스트도 실행한다.

```sh
xvfb-run -a .venv/bin/python -m unittest discover -s tests -v
```

이전 환경에는 Xvfb 대신 Xorg/xauth로 임시 DISPLAY :87을 만들어 테스트했다.
그때의 `/tmp/fm-queue-all.sh` 같은 개인 임시 도구는 새 환경에 있다고 가정하지 않는다.
`.venv` Python 3.12/Tk 9와 추가 Tk 8.6 환경의 검증 이력이 있으나 새 환경에서 재확인한다.

네이티브 회귀 테스트:

```sh
dotnet run --project plugin-src/FMFaceRefresh.Tests -c Release
dotnet run --project plugin-src/FMFaceRefresh.Diagnostics.Tests -c Release
```

정적 수집기 검사 절차는 `tools/FMRefreshMetadata/README.md`를 따른다.
인수인계 작성 시 GUI를 포함한 전체 Python 테스트 **448개가 28.955초에 모두 통과**했다.
이는 현재 Cloud 환경의 결과이며 Windows 설치본·실제 유료 합성의 재검증을 뜻하지 않는다.
실제 Codex 이미지 생성은 테스트에서 모의 응답을 쓰며 유료 호출하지 않는다.

실제 파일 검증 이력:

| 항목 | 확인 범위 |
|---|---|
| 27.1.0 세이브 | 선수 95,386명, 구단 팀 판정 47,155개 |
| 27.1.1 세이브 | 선수 95,050명, 구단 팀 판정 47,155개 |
| 원시 팀 테이블 | 양쪽 55,063개(국가대표 포함), 고유 ID/소유/주요 구조 비교 |
| 클럽 참조 | 21,445개 구단의 그래프 일치 |
| 판정 결과 | first 21,445 / reserve 2,910 / youth 9,709 / unknown 13,091 |
| 원래 실게임 팀 대조 | 47개 구단·147개 고유 팀, 154개 관찰 결과와 판정 비교 |
| 패치 전→후 | 임시 작업 공간의 기준 갱신·팀 판정·대기열 추가 검사, 원본/유료 호출 변경 없음 |

unknown 13,091은 전체 팀 테이블의 미검증 상태 등을 포함하며, 모든 선수 생성이 보류됐다는 뜻이 아니다.
새 빌드의 fmsave UnknownBuildWarning은 남아 있다. 구조 검사가 모든 필드 의미의 실게임 검증은 아니다.
동일 세이브를 몇 번 통과한 것으로 모든 커리어/DB/플랫폼 호환을 주장하지 않는다.
