# FM Face Automator 코드·메모리 점검

검토 기준: `8c1add3`, 앱 v1.0. 점검일: 2026-11-23(한국 시간).
최초 점검은 보고서만 추가했다. 아래 문제의 후속 수정·재검증 결과는 문서 마지막에 기록했다.

앱/엔진, 자료 탐색·이미지 처리, 저장·복구, 비동기 검색, 배포·설치 코드 및 네이티브
조회/새로고침 서비스의 자원 정리 경로를 검토했다. 아래 수치는 Linux 임시 자료로
재현한 결과다. 실제 Windows 프로세스의 전체 RAM이나 FM27 내부 메모리 측정값이 아니다.

## 1. 우선 수정: 복구 오류 시 PNG/XML의 부분 변경

위치: `facepack.py:102–126`, 특히 이미지 변경 후 XML을 쓰는 121–126행.

`restore()`는 이미지를 복구하거나 삭제한 다음 config.xml을 저장한다. 마지막 XML 쓰기가
실패했을 때 이미지 변경을 되돌리는 처리가 없다. `apply()`에 있는 예외 시 이미지 복원과 다르다.

임시 페이스팩에 이전/새 이미지를 만들고, 복구 마지막 XML 쓰기에서 OSError를 발생시켰다.
오류가 반환됐지만 PNG는 이전 이미지로 바뀌고 XML은 새 이미지 적용 당시 내용으로 남았다.
복구 전 백업은 남으므로 백업 자체가 사라지는 문제는 아니지만, 실패 후 자동 일관성이 없다.

개선: 복구 전 PNG/XML 상태를 보관하고 쓰기 실패 시 둘의 이전 상태를 되돌린다.
기존 이미지가 없었던 경우의 삭제도 함께 되돌리며, 이 오류 경로를 회귀 테스트로 추가한다.

## 2. 우선 수정: UI 갱신이 DB 쓰기 잠금을 기다림

위치: `app.py:1647`, `engine.py:484`, `engine.py:507`.

Tk 메인 스레드의 주기적 `drain()`이 `Engine`을 생성한다. Engine 생성자는 읽기만 하는
객체가 아니라 테이블 확인과 메타데이터 쓰기를 수행하며 SQLite timeout은 20초다.
백그라운드 세이브 반영이 쓰기 트랜잭션을 오래 유지하면 UI 콜백도 그 잠금을 기다릴 수 있다.

별도 연결로 BEGIN IMMEDIATE 잠금을 잡고 0.35초 뒤 해제한 모의 조건에서
Engine 생성·종료가 약 0.431초 걸렸다. 실제 Windows 화면 정지를 측정한 것은 아니지만,
같은 생성자가 메인 스레드에서 호출되고 있음을 코드로 확인했다.

추가 부담: `engine.py:930`의 최근 결과 조회는 메모리에는 제한된 배치를 보관하지만
아티팩트가 있는 작업 전체를 훑으며 파일 stat을 수행한다. 이 조회도 UI 갱신 경로에 있다.

개선: UI는 쓰기를 하지 않는 읽기 전용 스냅샷을 받고, DB 잠금 시 해당 갱신을 건너뛴다.
파일 이력 검색도 작업 스레드로 옮겨 메인 스레드가 디스크 I/O를 기다리지 않게 한다.

## 3. 메모리: 참조 사진 미리보기로 원본 크기의 RGBA를 보관

위치: `manual_ui.py:105–114`, `manual_ui.py:127–128`, `assets.py:319–332`.

화면의 작은 미리보기만 필요한데 reference_png() 결과를 다시 열어 원본 크기로 복사하고
reference_image에 보관한다. 창 크기 변경 시 이 전체 이미지를 또 복사한 후 축소한다.

4096×4096 RGB PNG(약 57.3KiB)를 실제 변환 경로로 불러온 모의 확인에서 보관된
미리보기는 4096×4096 RGBA였다. 픽셀 버퍼만 64MiB이며 그리기의 추가 복사도 같은 크기다.
현재 허용하는 8192×8192 RGBA는 버퍼 하나만 256MiB다. 이는 프로세스 RSS 측정이 아닌
확인한 크기·모드로 계산한 픽셀 버퍼 용량이며 Pillow/Tk 임시 메모리는 별도다.

개선: 미리보기용 사본만 작은 크기로 한 번 축소해 보관한다. 원본 경로는 그대로 보관하고
원본 파일은 변경하지 않는다. 전송용 참조 이미지의 크기 제한은 별도로 결정한다.

## 4. 메모리·I/O: 전체 색인과 XML 중복 로딩

위치: `assets.py:197–236`, `facepack.py:64–85`, `engine.py:538–548`.

AssetCatalog는 전체 매핑 색인을 만든다. XML 원문, 파싱 요소, 임시 records 목록과
여러 색인 구조가 한동안 함께 존재한다. 이는 무조건 불필요한 데이터라고 할 수는 없지만
대형 팩에서 메모리 피크를 높인다. 저장 시 apply()가 이미 읽은 XML을 snapshot()이 다시
읽고 파싱하는 중복도 있다. 캐시는 파일 변경이 없어도 60초가 지나면 다시 구축한다.

같은 파일을 참조하는 서로 다른 선수 매핑 1만 개로 Python heap을 tracemalloc 측정했다.

| 작업 | 관측값 |
| --- | --- |
| 전체 AssetCatalog 유지 | 약 9.02MiB |
| 색인 생성 중 피크 | 약 9.59MiB |
| 색인 참조 해제 후 GC | 반올림 기준 0.00MiB |
| XML 한 번 load() 피크 | 약 5.93MiB |
| 같은 자료의 apply() 피크 | 약 11.76MiB |

이 수치는 모의 자료의 Python 할당만 나타내며 전체 앱 RAM과 동일하지 않다.
색인 해제 후 메모리가 회수됐으므로 이 결과는 지속적인 누수 증거가 아니다.

개선: 검증·매핑 우선순위는 보존하면서 저장/백업에 같은 원문을 재사용하고
중간 목록을 줄인다. 캐시 갱신은 XML 변경이나 검색 실패에 근거해 수행하도록 검토한다.

## 5. 부하 시 메모리·CPU: 검색 스레드 수가 제한되지 않음

위치: `app.py:1002–1028`, `manual_ui.py:135–139`, `player_catalog.py:18`.

검색 입력에는 debounce가 있지만, 이미 시작한 검색을 취소하거나 실행 수를 제한하지 않는다.
결과 토큰은 오래된 결과를 화면에서 버릴 뿐, 그 검색과 DB 연결을 종료하지 않는다.

검색 함수를 대기하도록 모의하고 12번 호출했을 때 12개 작업 스레드가 동시에 살아 있었다.
실제 선수 DB에서 그만큼 느리다는 측정은 아니며, 느린 DB에서 중첩될 수 있는 구조의 재현이다.

개선: 화면별 검색 작업을 하나만 실행하고 최신 요청 한 개만 대기시킨다.
가능하면 SQLite progress handler 등으로 오래된 검색을 중단한다.

## 기존에 제한·정리가 확인된 부분

- 화면 로그는 2,000줄/512,000자 상한이 있다.
- 최근 결과는 5개만 보관하고 화면 이미지는 선택한 항목을 표시한다.
- Engine.close()가 자료 색인을 해제하며, 색인 교체 전 이전 참조를 해제하는 테스트가 통과한다.
- Codex 실행 로그는 파이프 누적 대신 파일로 출력한다.
- 팀 조회의 임시 그룹 Dispose와 전용 루트 Remove, 참조 Clear가 finally 경로에 있다.
- 네이티브 최근 조회 기록은 8건으로 제한한다. 늦게 도착하는 새로고침 콜백은 의도적으로
  보관하며 128건에서 안전 제한을 건다. 이를 임의로 해제하는 수정은 제안하지 않는다.
- 배포는 검증된 프로그램 파일 목록을 사용하며 사용자 설정·페이스팩을 대상으로
  광범위한 삭제 규칙을 두지 않는다. 실제 Inno 설치/제거 동작은 Windows 확인이 남아 있다.

## 검증 결과와 남은 한계

- 기존 Python 테스트 384개 통과(GUI 테스트 포함).
- FMTeamBindings.Tests, FMFaceRefresh.Tests, FMFaceRefresh.Diagnostics.Tests,
  FMTeamMetadata.Tests의 .NET 테스트 실행 통과. 네이티브 어댑터는 가짜 게임 API 검증이다.
- 위 복구 실패, DB 잠금, 참조 사진, 메모리 및 검색 중첩 재현은 임시 파일과 모의 조건만 사용했다.
  사용자 세이브·이미지·설정을 열거나 변경하지 않았고 Codex 유료 호출도 하지 않았다.
- 기존 테스트 통과는 이번에 확인한 오류·고부하 경로가 정상이라는 뜻이 아니다.
- Windows EXE의 장시간 RAM, 실제 .fm 파싱 피크, 실제 게임 네이티브 메모리 및
  Inno Setup의 실제 설치·업데이트·제거는 이번 환경에서 측정하지 않았다.

수정 우선순위는 복구 실패 일관성 → UI DB 대기 → 미리보기 메모리 → XML/색인 → 검색 작업 제한이다.

## 후속 수정 및 재검증

사용자가 제공한 ponytail(full) 기준으로 기존 경로를 재사용해 다섯 항목을 수정했다.
새 의존성·설정 옵션·게임 DLL 변경은 없다.

- apply/restore가 공통 파일 교체·실패 복원 처리를 사용한다. 이미지 복구와 삭제,
  XML 저장 전/후 오류를 주입해 원래 PNG/XML 또는 파일 부재 상태가 복원됨을 확인했다.
  복원 자체가 실패하면 가능한 나머지 파일의 복원을 시도하고 백업 위치를 오류로 알린다.
- 주기적인 Engine 생성·DB 조회·최근 이미지 이력 조회를 하나의 작업 스레드로 옮겼다.
  Tk에는 결과 데이터만 전달하며, 오래된 결과와 다른 세이브의 결과는 적용하지 않는다.
  DB 쓰기 잠금 중에도 Tk 이벤트가 처리되는 것을 GUI 테스트로 확인했다.
  직접 삭제·순서 변경 같은 명시적 사용자 작업의 기존 DB 처리 경로는 유지한다.
- 참조 사진은 검증 후 미리보기용만 최대 512×512로 축소한다. 원본 파일·요청 경로와
  실제 합성에 사용하는 기본 참조 처리에는 크기 변경을 적용하지 않는다.
- XML 원문을 저장과 백업에 재사용한다. 복구할 때는 백업에서 대상 선수의 매핑만 남긴 뒤
  현재 XML을 읽는다. 색인 파싱 중 빈 요소와 중간 목록을 해제한다.
- 60초마다 무조건 전체 색인을 재구축하던 동작을 변경했다. 디렉터리·XML 변화 또는
  검색 실패가 있을 때 갱신하며, XML 해시로 크기·mtime을 보존한 변경도 확인한다.
- 선수 검색은 화면별 작업 하나와 최신 대기 요청 하나만 유지한다. 오래된 검색은 SQLite
  progress handler로 중단하며, 종료 시 취소한다. 다른 세이브로 바뀐 뒤 이전 작업 선택을
  이용해 삭제할 수 없도록 보호한다.

같은 모의 자료로 다시 측정한 결과:

| 항목 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 4096×4096 참조 사진의 보관된 미리보기 RGBA 버퍼 | 64MiB | 1MiB |
| 1만 매핑의 apply() Python heap 피크 | 11.76MiB | 6.53MiB |
| 1만 매핑의 AssetCatalog 생성 피크 | 9.59MiB | 9.03MiB |
| XML 저장 오류 후 복구 상태 | 이미지/XML 부분 변경 | 이전 상태 복원 |
| 느린 검색 중 연속 20개 추가 요청 | 요청별 스레드 | 첫 작업 취소 후 최신 요청만 실행 |

전체 Python 테스트 397개와 별도 Tk 8.6 GUI 테스트 14개로 검증했다. 기존 매핑 우선순위,
원본·백업 바이트 보존, 오래된 UI 결과 제외, 세이브 전환, 오류 이후 폴링 유지도 검사했다.
실제 Windows·게임의 RAM과 장시간 실행, 장치 오류 시의 복구 가능 여부는 여전히 별도 확인이 필요하다.
대형 페이스팩의 전체 매핑 색인 자체에 필요한 메모리는 남아 있다.
